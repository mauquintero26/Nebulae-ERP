### 2.2. Módulo Financiero ERP (`backend/app/api/v1/finance.py`)
- **Protección RBAC Estricta:**
  - Inyección de dependencia `require_roles(*ROLE_ADMIN, *ROLE_FINANZAS)` en las 6 rutas financieras:
    1. `GET /api/v1/finance/accounts-receivable` (Cartera pendiente y saldos por cobrar).
    2. `GET /api/v1/finance/accounts-payable` (Cuentas por pagar a proveedores desde PEC).
    3. `GET /api/v1/finance/ledger/reconciliation` (Reconciliación de libro mayor y flujo de caja).
    4. `GET /api/v1/finance/inventory-valuation` (Valoración contable separada NEBULAE vs MAU).
    5. `GET /api/v1/finance/losses-and-scrap` (Reporte de mermas y scrap).
    6. `GET /api/v1/finance/profitability` (Rentabilidad global y márgenes).
- **Control de Acceso y Respuestas:**
  - Petición anónima (sin Bearer token): Retorna `401 Unauthorized`.
  - Roles no autorizados (`ASESOR`, `BODEGA`, `COMPRAS`): Retorna `403 Forbidden`.
  - Roles autorizados (`ADMIN`, `FINANZAS`): Retorna `200 OK` con payload íntegro.
- **Deduplicación de Pérdidas y Scrap:**
  - Deduplicación canónica entre `InventoryMovement` con `direction="SCRAP"` y `SaleOrderReturnLine` con `inventory_resolution="DESTRUIDO"`.
  - Evita el doble conteo contable utilizando el prefijo determinista `mov-ret-scrap-{return_line_id}` en `idempotency_key`.

### 2.3. Módulo CRM 360 y Privacidad de Datos (`backend/app/api/v1/crm.py`)
- **Eliminación de `get_optional_current_user`:** Se exige autenticación estricta con `get_current_active_user`. Sin token retorna `401 Unauthorized`.
- **Proyecciones de Datos por Rol:**
  - `ADMIN` / `FINANZAS`: Acceso irrestricto a perfil 360, rentabilidad histórica, costos unitarios, márgenes brutos, pagos, cartera y trazabilidad operativa.
  - `ASESOR`: Vista comercial completa pero con confidencialidad de costos. Se retorna `rentabilidad = {"visible": False, "motivo": "Requiere rol administrativo o financiero"}`, y se omiten `costo_total_cop` y porcentajes de margen en el listado de pedidos.
  - `BODEGA`: Acceso estrictamente logístico para despacho y empaque. Se enmascaran u ocultan datos privados: `phone = None`, `email = None`, `document = None`, `resumen_financiero = None`, `pagos = []`, ocultando información financiera innecesaria para el rol.
  - `COMPRAS`: Acceso enfocado a aprovisionamiento y compras vinculadas. Se omiten datos de contacto personal y pagos del cliente.

### 2.4. Módulo de Chat y Asistente Omnicanal (`backend/app/api/v1/chat.py`)
- **Arquitectura de Autenticación Dual:**
  - *Contexto Interno ERP:* Token Bearer de usuario autenticado con roles validados.
  - *Contexto Cliente Autoservicio:* Token JWT seguro y firmado (`sub` = customer_id o payload con `customer_id`), con expiración y revocación.
- **Prevención Anti-IDOR Inviolable:**
  - Si un cliente autenticado con token propio intenta consultar o enviar mensajes a nombre de un `customer_id` ajeno en el body, la solicitud es rechazada inmediatamente con `403 Forbidden`.
- **Auditoría Protegida:**
  - Endpoint `GET /omnichannel/interactions` protegido con RBAC (`ADMIN` y `ASESOR`).
  - Cada interacción registra de forma inmutable: `customer_id`, canal (`WHATSAPP`, `WEB_CHAT`, etc.), `agent_id` (o bot), mensaje, metadatos y timestamp.

### 2.5. Módulo Ecommerce y Checkout Seguro (`backend/app/api/v1/ecommerce.py`)
- **Cálculo Server-Side Inviolable (Fuente Única de Verdad):**
  - El cliente solo envía: identificación del cliente, líneas con `sku` y `quantity`, dirección de entrega, método de entrega y la `idempotency_key`.
  - El servidor calcula desde la base de datos: precio unitario, descuentos autorizados, impuestos, subtotal y total. Cualquier payload del cliente con precios manipulados es rechazado con `422 Unprocessable Content`.
- **Bloqueo Patrimonial:**
  - Validación estricta que prohíbe explícitamente vender stock custodiado o perteneciente a `MAU` a través del checkout ecommerce. Intentos de venta de stock `MAU` son rechazados con `400 Bad Request` / `403 Forbidden`.
- **Disponibilidad Vendible Pesimista:**
  - Utiliza la fórmula canónica de reservas: $	ext{disponible} = 	ext{InventoryOwnerBalance} - 	ext{Reservas Activas}$.
  - Si el stock vendible es inferior a la cantidad solicitada, la orden se rechaza con `409 Conflict` antes de escribir cualquier registro.
- **Idempotencia con Fingerprint Criptográfico:**
  - Se genera un fingerprint SHA-256 canónico a partir de: `customer_id`, líneas ordenadas `[(sku_id, qty)]`, `shipping_address`, `delivery_method` y `currency`.
  - Caso 1 (Nuevo pedido): Se crea la orden con `201 Created` y se guardan `checkout_idempotency_key` y `checkout_fingerprint`.
  - Caso 2 (Replay idéntico): Misma clave y misma huella retorna `200 OK` con los datos del pedido ya existente e `idempotent_replay = True`.
  - Caso 3 (Conflicto / Divergencia): Misma clave pero payload alterado retorna `409 Conflict`.
- **Secuencia y Estado Inicial:**
  - Asignación atómica mediante secuencia PostgreSQL: `PWEB-YYYY-#####`.
  - Estado inicial estricto: `PENDIENTE_PAGO`. Prohibido crear pagos confirmados durante el checkout.

### 2.6. Módulo de Webhooks de Pasarela (`backend/app/api/v1/webhooks.py`)
- **Allowlist de Proveedores:**
  - Validación cerrada de pasarelas aceptadas (`wompi`, `mercadopago`, `bold`, `stripe`, `tucompra`). Proveedores no reconocidos son rechazados con `400 Bad Request`.
- **Verificación Criptográfica HMAC en Tiempo Constante:**
  - Verificación mediante `hmac.compare_digest` para neutralizar ataques de canal lateral por temporización (timing attacks).
  - Si el header de firma está ausente o la firma no coincide, se rechaza de inmediato con `401 Unauthorized`.
  - Fallback a formatos normalizados de serialización JSON para pasarelas que compactan el cuerpo.
- **Sanitización de Cabeceras Sensibles:**
  - Función `_sanitize_headers` que enmascara como `[REDACTED]` las cabeceras sensibles (`Authorization`, `Cookie`, `X-Signature`, `X-Api-Key`, `Token`, `Secret`) antes de persistir el evento en base de datos.
- **Confirmación Exacta de Pago en Ledger:**
  - El webhook procesa el pago solo si el estado es aprobado y el monto notificado coincide con el `total_cop` de la orden de venta.
  - Al coincidir: registra `SaleOrderPayment(tipo="PAGO_TOTAL", estado="CONFIRMADO")`, actualiza `SaleOrder(estado="PAGADO", saldo_cop=0)` y marca el webhook como `PROCESSED`.
  - Montos discordantes o eventos no aprobados NO confirman el pago ni modifican el ledger.
- **Gestión de Reintentos y Dead-Letter:**
  - Endpoint `POST /api/v1/webhooks/{id}/retry` protegido exclusivamente para rol `ADMIN`.
  - Flujo de estados: `RECEIVED` -> `PROCESSING` -> `PROCESSED` (o `FAILED` -> `DEAD_LETTER` al superar el límite de reintentos).

### 2.7. Módulo de Marketing y Habeas Data (`backend/app/api/v1/marketing.py`)
- **Cumplimiento Estricto de Ley 1581 de 2012:**
  - Los consentimientos inician obligatoriamente en `False`. Prohibido el opt-in tácito o automático.
  - Al registrarse o actualizarse consentimientos, se capturan metadatos de auditoría: `legal_version`, `legal_basis`, canal, fecha, IP y user-agent.
- **Anti-IDOR en Autoservicio de Clientes:**
  - Actualización de preferencias vía token propio del cliente (o rol administrativo interno). Intentos de modificar consentimientos de terceros son bloqueados con `403 Forbidden`.
- **Segmentación Protegida por RBAC:**
  - Endpoint `GET /api/v1/marketing/segmentacion` reservado a roles comerciales autorizados (`ADMIN` y `ASESOR`). Usuarios anónimos reciben `401 Unauthorized` y roles no autorizados como `BODEGA` reciben `403 Forbidden`.

## 5. CATÁLOGO DE ATAQUES Y VULNERABILIDADES MITIGADAS

| Vector de Ataque | Escenario de Prueba | Mitigación Implementada | Código HTTP Esperado y Obtenido |
|---|---|---|:---:|
| **Manipulación de Precios (Price Tampering)** | Cliente envía `unit_price_cop: 1000` en producto con precio oficial de `$350,000 COP` | Servidor recalcula exclusivamente desde `ProductSKU` e ignora o rechaza precios manipulados | **422 Unprocessable Content** |
| **Bypass Patrimonial (Owner Tampering)** | Petición de compra de stock custodiado por `MAU` | Validación que restringe el checkout ecommerce únicamente a inventario `NEBULAE` | **400 Bad Request** / **403 Forbidden** |
| **Sobreventa por Concurrencia (Overselling)** | Dos compradores intentan adquirir simultáneamente la última unidad | Verificación pesimista contra `InventoryOwnerBalance` restando reservas activas | **409 Conflict** |
| **Falsificación de Webhooks (HMAC Spoofing)** | Petición HTTP a `/webhooks/{provider}` con firma inválida o ausente | Verificación criptográfica con `hmac.compare_digest` y secreto de pasarela | **401 Unauthorized** |
| **Ataque IDOR en Asistente Omnicanal** | Cliente A envía consulta adjuntando `customer_id` del Cliente B | Validación del token de cliente autoservicio contra el customer solicitado | **403 Forbidden** |
| **Ataque IDOR en Habeas Data** | Cliente A intenta revocar o alterar consentimientos del Cliente B | Enlace criptográfico entre el token de sesión y el ID del cliente | **403 Forbidden** |
| **Fuga de Credenciales en Logs** | Webhook entrante con Bearer token y cookies en encabezados | Sanitización sistemática sustituyendo valores por `[REDACTED]` | **200 OK (Persistencia Sanitizada)** |
| **Conflicto de Idempotencia por Replay Alterado** | Misma `idempotency_key` enviada con diferente carrito o dirección | Comparación de huella canónica SHA-256 (`checkout_fingerprint`) | **409 Conflict** |
| **Acceso a Datos Financieros Sensibles** | Asesor comercial solicita balance contable o libro mayor | Inyección de roles permitidos (`ADMIN`, `FINANZAS`) | **403 Forbidden** |
