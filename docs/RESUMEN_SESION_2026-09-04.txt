BLOQUEO 1 — quantity_received: semántica inequívoca
════════════════════════════════════════════════════════════════════

PROBLEMA CORREGIDO:
  La regla "if quantity_received == 0 and quantity_expected > 0:
             quantity_received = quantity_expected" fue eliminada.
  El valor cero ya NO se interpreta como recepción completa.

IMPLEMENTACIÓN:
  1. Migración fa1b_005: ALTER COLUMN quantity_received DROP NOT NULL
     - NULL = cantidad aún no registrada por el operador
     - Ceros en BORRADOR convertidos a NULL automáticamente
  2. Modelo: GoodsReceiptLine.quantity_received = Column(Numeric, nullable=True, default=None)
  3. Nuevo endpoint: PATCH /recepciones/{eninv_id}/lineas/{grl_id}
     - Registra quantity_received (None o int), quantity_rejected, quantity_quarantine
     - Solo funciona si la recepción está en BORRADOR
     - Roles: ADMIN, COMPRAS, BODEGA
  4. confirmar_recepcion:
     - Si GRL.quantity_received is None y receipt_type="FISICA" → 422
       "La línea GRL {id} no tiene cantidad registrada. Usa PATCH /lineas/{id}
        para registrar la cantidad antes de confirmar. Registra 0 si no llegó nada."
     - Si is None y LOGISTICA → qty=0 (sin impacto en stock, válido)
     - 0 explícito → válido, no suma al stock
     - >0 → suma al inventario como siempre
  5. crear_recepcion_desde_pec: GRL creada con quantity_received=None
  6. POST /recepciones: GRL creada con quantity_received=None

DISTINCIÓN INEQUÍVOCA:
  NULL         = pendiente de registro (operador no ha actuado)
  0            = registrada explícitamente en cero (no llegó nada)
  >0           = cantidad recibida registrada
  rejected     = campo quantity_rejected (unidades devueltas)
  quarantine   = campo quantity_quarantine (unidades en cuarentena)

BLOQUEO 2 — Normalizar caminos de creación y edición
════════════════════════════════════════════════════════════════════

PROBLEMA CORREGIDO:
  - POST /recepciones creaba GoodsReceipt sin GoodsReceiptLine
  - PATCH /recepciones modificaba JSON independientemente de GRL
  - PATCH /pedidos modificaba productos sin sincronizar PurchaseOrderLine

IMPLEMENTACIÓN:

  POST /recepciones (create_recepcion):
    → db.add(gr); db.flush()
    → for prod in body["productos"]: db.add(GoodsReceiptLine(..., quantity_received=None))
    → db.commit()
    → GRL creadas atómicamente en la misma transacción

  PATCH /recepciones/{id} (update_recepcion):
    → Si body trae "productos" Y estado == "BORRADOR":
        Actualiza GRL existentes (por índice, preservando IDs)
        Regenera g.productos desde GRL (JSON como snapshot, no fuente)
    → Si body trae "productos" Y estado != "BORRADOR":
        422 "No se puede modificar productos de una recepción en estado X"
    → Otros campos (notas, carrier, etc.): sin cambio en comportamiento

  PATCH /recepciones/{id}/lineas/{grl_id} (NUEVO):
    → Solo en BORRADOR
    → Actualiza quantity_received, quantity_rejected, quantity_quarantine
    → Retorna la GRL actualizada

  PATCH /pedidos/{id} (update_pec):
    → Si body trae "productos" Y COUNT(goods_receipts WHERE pec_id) > 0:
        409 "La PEC ya tiene recepciones. Cambios estructurales no permitidos."
    → Si body trae "productos" Y sin recepciones:
        DELETE FROM purchase_order_lines WHERE pec_id
        INSERT PurchaseOrderLine por cada producto del body
        p.productos = body["productos"]  (snapshot)

BLOQUEO 3 — Recepciones parciales por po_line_id (no sku_id)
════════════════════════════════════════════════════════════════════

PROBLEMA CORREGIDO:
  ya_recibidas agrupaba por sku_id → falla con 2 líneas del mismo SKU en una PEC.

IMPLEMENTACIÓN:
  Ruta normalizada (PEC con purchase_order_lines):
    ya_recibidas_pol = SQL:
      SELECT grl.po_line_id, COALESCE(SUM(grl.quantity_received), 0)
      FROM goods_receipt_lines grl
      JOIN goods_receipts gr ON gr.id = grl.gr_id
      WHERE gr.pec_id = :pec AND gr.stock_actualizado = true
        AND grl.po_line_id IS NOT NULL
      GROUP BY grl.po_line_id
    → {po_line_id: qty_acumulada}
    → Loop itera _pol_rows (purchase_order_lines ORDER BY id)
    → Cada POL con saldo genera 1 GoodsReceiptLine
    → quantity_pending = quantity_ordered - ya_recibidas_pol[pol_id]

  Fallback legacy (PEC sin purchase_order_lines):
    → Calcula ya_recibidas_sku por sku_id desde GRL confirmadas
    → Si no hay GRL: lee JSON de recepciones confirmadas (fallback-de-fallback)
    → Itera p.productos como antes
    → _po_line_id = None en las GRL creadas
