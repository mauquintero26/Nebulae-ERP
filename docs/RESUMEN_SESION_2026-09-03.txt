5. CICLO DE VIDA DE IDEMPOTENCIA (2 transacciones independientes)
============================

  Tx1 -- corta, independiente (SessionLocal distinto):
    INSERT INTO idempotency_requests (..., status='PROCESSING', execution_token=UUID,
      request_body=CAST(:body AS jsonb)) ON CONFLICT (op_type, op_key) DO NOTHING
    idem_session.commit()  <- persiste independientemente de Tx2
    Si rowcount == 1: este proceso gano el lock
    Si rowcount == 0: otra ejecucion tiene la clave
      -> leer registro existente
      -> si DONE: replay 200
      -> si PROCESSING: 409 "operacion en proceso"
      -> si FAILED: 409 "operacion fallida anteriormente"

  Tx2 -- principal (db del endpoint FastAPI):
    SELECT FOR UPDATE GoodsReceipt (bloquea fila ENINV)
    Validaciones de negocio
    SELECT FOR UPDATE InventoryLevel por cada SKU
    UPDATE inventory_levels SET quantity += qty_recibida
    INSERT InventoryOperation (uq_inv_op_source_doc previene duplicados)
    INSERT InventoryMovement
    UPDATE GoodsReceipt SET stock_actualizado=True, estado=COMPLETADA
    UPDATE idempotency_requests SET status='DONE',
      response_body=CAST(:resp AS jsonb), completed_at=now
    db.commit()

  Si Tx2 falla -> db.rollback() + _mark_failed_external()
    Opera en SessionLocal() separado (Tx1 ya fue committed).
    UPDATE ... WHERE op_key=:k AND execution_token=:token AND status='PROCESSING'
    La condicion AND execution_token garantiza que solo el proceso propietario
    puede marcar FAILED; si otra ejecucion ya puso DONE, el UPDATE no toca nada.

6. LOGICA DE NEGOCIO -- confirmar_recepcion
============================

  ENINV ya confirmada (stock_actualizado=True):
    misma clave + mismo hash   -> replay 200 (desde response_body JSON en BD)
    misma clave + hash diferente -> 409 "payload no coincide"
    clave diferente             -> 409 "ya confirmada con diferente clave"
    NUNCA crea otro InventoryOperation
    NUNCA devuelve 500
    NUNCA depende de constraint para detenerse

  ENINV cancelada/completada/LOGISTICA-ya-confirmada -> 409 / replay segun clave

  Recepcion FISICA:
    Incrementa inventory_levels.quantity por SKU
    stock_actualizado = True, estado ENINV = COMPLETADA
    Calculo acumulado del estado PEC:
      Consulta TODAS las recepciones FISICAS confirmadas de la PEC
      qty_acumulada por SKU = suma(otras) + qty_actual
      pendiente > 0  -> PEC = PARCIALMENTE_RECIBIDA
      pendiente == 0 -> PEC = RECIBIDA

  Recepcion LOGISTICA:
    NO incrementa stock (inventory_levels sin cambio)
    stock_actualizado = False
    estado ENINV = COMPLETADA_LOGISTICA
    PEC NO avanza (ni parcial ni recibida)

  Validaciones (Pydantic + negocio):
    idempotency_key obligatoria (min 8, sin default en backend)
    receipt_type en whitelist FISICA | LOGISTICA
    qty_recibida < 0          -> 422
    qty_recibida > esperada sin allow_excess -> 422
    Sin productos validos para FISICA -> 422
    Sin bodega                -> 400

  crear_recepcion_desde_pec:
    Descuenta recepciones FISICAS ya confirmadas antes de copiar cantidades.
    qty_pendiente = max(0, qty_total - ya_recibidas[sku])
    Si todos los SKUs en 0 -> 400 "PEC completamente recibida"
    force_full=True disponible para registrar excedentes.
