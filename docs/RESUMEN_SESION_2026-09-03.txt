FASE 1B CORRECCION ARQUITECTURAL — COMPLETADA (commit f617d78)
---------------------------------------------------------------
Problema identificado: confirmar_recepcion seguia leyendo g.productos
para calcular inventario. GoodsReceiptLine era aditiva, no la fuente de verdad.

CORRECCIONES IMPLEMENTADAS:

1. create_pec (POST /api/v1/compras/pedidos)
   - Ahora crea PurchaseOrderLine por cada producto del payload.
   - Una fila por linea, independientemente del sku_id (permite SKUs duplicados).

2. crear_recepcion_desde_pec (POST /pedidos/{pec_id}/recepcionar)
   - Construye mapa FIFO {sku_id: deque[po_line_id]} desde purchase_order_lines.
   - Por cada producto pendiente: asigna po_line_id via popleft() (no LIMIT 1).
   - Crea GoodsReceiptLine en la MISMA transaccion (db.flush() + db.add GRL).
   - GRL creada con quantity_received=0, source='NATIVE'.

3. confirmar_recepcion (POST /recepciones/{id}/confirmar)
   - SELECT FOR UPDATE GoodsReceiptLine WHERE gr_id=eninv_id ORDER BY id.
   - Fallback para recepciones legacy (sin GRL preexistentes): crea GRL
     desde JSON snapshot, usando quantity_expected (no qty_recibida del JSON).
   - Validaciones y calculo de sku_increments exclusivamente desde GRL:
       - quantity_expected, quantity_received, quantity_rejected,
         quantity_quarantine, sku_id, receipt_type
   - Actualiza GRL in-place (NO DELETE+INSERT — conserva IDs para trazabilidad).
   - Regenera g.productos como SNAPSHOT desde GRL (GRL -> JSON, no al reves).
   - Estado PEC calculado desde purchase_order_lines + goods_receipt_lines (SQL).
   - Fallback estado PEC: acumula GRL de recepciones previas confirmadas
     + GRL de otras ENINV via JSON (si no hay GRL previas).
