### Bloqueo 2: Retry después de FAILED e Idempotencia Robusta
- **Persistencia Atómica Completa en `_mark_failed_external`:**
  - Se persisten de manera atómica todos los atributos requeridos en `idempotency_requests`: `operation_type`, `operation_key`, `request_hash`, `request_body`, `execution_token`, `entity_type`, `user_id`, `status='FAILED'`, `error_detail`, `created_at` y `completed_at`.
  - Se reemplazó cualquier manejo genérico silenciado por logging estructurado con `logger.error` e inclusión de traceback.
  - Se implementó protección con fallback para `user_id = NULL` ante posibles inconsistencias de integridad referencial, asegurando que el registro de fallo nunca se pierda.
- **Ciclo de Vida de Retry:**
  - Un reintento con payload idéntico sobre una operación en estado `FAILED` genera un nuevo `execution_token` persistido y permite reiniciar la ejecución como `PROCESSING`.
  - Si se soluciona la causa del error (ej. se incrementa el stock o se activa la entidad), la operación concluye exitosamente y transiciona a `status='DONE'`.
  - Una tercera llamada con idéntico payload detecta `status='DONE'` y responde inmediatamente como replay idempotente seguro `200 OK` con `idempotent_replay: true`.
  - Un reintento con un payload que difiere en su contenido genera un `request_hash` divergente y es rechazado estrictamente con `HTTP 409 Conflict`.
- **Diferenciación de Códigos HTTP (201 Created vs 200 OK):**
  - En `POST /api/v1/inventory/reservas`, la primera creación exitosa responde con `201 Created`. Sin embargo, cualquier llamada replay posterior responde explícitamente con `200 OK`, utilizando inyección de `Response` en FastAPI.
- **Casos de Hardening 16, 17, 18 y 19:**
  - Se crearon y verificaron pruebas exhaustivas que validan este ciclo completo para:
    1. Caso 16: `crear_reserva` (Fallo 409 -> Retry 201 -> Replay 200 -> Conflicto por divergencia 409).
    2. Caso 17: `convertir_reserva` (Fallo 409 -> Retry 200 -> Replay 200 -> Conflicto por divergencia 409).
    3. Caso 18: `liberar_reserva` (Fallo 409 -> Retry 200 -> Replay 200 -> Conflicto por divergencia 409).
    4. Caso 19: `resolver_cuarentena` (Fallo 409 -> Retry 200 -> Replay 200 -> Conflicto por divergencia 409).

### Bloqueo 3: Reversibilidad Completa de Migraciones (Roundtrip)
- **Downgrade `fa3_001` hacia `fa2_003`:**
  - En `backend/alembic/versions/fa3_001_recepciones_inventario.py`, antes de truncar la columna `direction` de `inventory_movements` a `VARCHAR(10)`, se ejecutan sentencias de conversión de datos para acortar valores que superen 10 caracteres:
    - `UPDATE inventory_movements SET direction = 'TR_IN' WHERE direction = 'TRANSFER_IN'`
    - `UPDATE inventory_movements SET direction = 'TR_OUT' WHERE direction = 'TRANSFER_OUT'`
  - Esto previene cualquier excepción por `value too long for type character varying(10)` durante el downgrade.
- **Downgrade `fa3_002` hacia `fa3_001`:**
  - En `backend/alembic/versions/fa3_002_cuarentena_owner_hardening.py`, la conversión de tipos `NUMERIC(10, 2)` a `INTEGER` utiliza `USING ROUND(quantity)::integer` para garantizar una reversión exacta sin pérdida ni truncado inesperado.
- **Prueba Integral de Roundtrip en `test_fase3_migrations.py`:**
  - `test_fa3_roundtrip_downgrade_upgrade` ejecuta y certifica físicamente el ciclo completo:
    `upgrade head -> downgrade fa3_001 -> downgrade fa2_003 -> upgrade head`
  - Comprueba detalladamente en cada etapa que los tipos de datos, longitudes de columna, nulabilidades, constraints `CHECK`, índices compuestos (`ix_quarantine_lookup`, etc.) quedan exactamente en el estado esperado y no subsisten objetos, columnas ni índices huérfanos.
